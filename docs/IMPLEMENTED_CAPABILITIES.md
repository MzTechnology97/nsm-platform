# NSM Platform — Implemented Capabilities

Status: living implementation reference

This document records **only functionality implemented in the repository**. It intentionally excludes planned or aspirational behavior.

When a feature becomes operational, update this document in the same development cycle. Open PRs, menu entries, placeholders and data models alone are not sufficient to classify a capability as implemented.

## Platform and inventory

Implemented:

- Customer, customer-local Site and Device hierarchy.
- Cross-customer Site assignment protection.
- Operator display name separated from observed Device identity.
- Device inventory fields for vendor, model, serial, MAC, architecture, management IP, observed firmware and source/verification metadata.
- Customer/device workspaces and global Device inventory.
- Customer/Device CRUD foundations.
- Device CSV import.
- Search across key Device identity fields.
- Responsive/theme/branding foundations.

## Users, permissions and API

Implemented:

- authenticated sessions;
- user administration foundations;
- permission checks on operational routes;
- granular permission names across device, monitoring, backup, firmware, security and audit workflows;
- user profile/password-change workflow with audit event;
- API key foundations and scoped operational API foundations.

This does not imply that all future delegated/scoped RBAC administration is complete.

## Audit, Action Center and notifications

Implemented:

- append-oriented audit event model;
- per-device Audit and Job/activity worklists;
- active queue separated from completed/history records;
- search/filter/date/pagination for scalable activity/audit worklists;
- global Audit Events filtering/pagination;
- filtered global Audit CSV export with export audit event;
- Action Center issue persistence, severity/category/status and acknowledgement workflow;
- in-app notifications, unread state, top-bar count and recent notification dropdown;
- selected automated Action Center/recovery behavior for implemented MikroTik workflows.

External notification channels are not claimed here.

## Backup control plane

Implemented:

- Backup Center and customer backup workspace foundations;
- backup policies and scope/inheritance foundations;
- capability-aware backup method guarding;
- distinction between configured policy and executable capability;
- manual `Backup ora` for supported devices;
- scheduled backup worker/retry/retention foundations;
- backup run/artifact history;
- authenticated artifact access;
- SHA-256 evidence where generated by the backup pipeline.

### MikroTik backup

Implemented on the supported agent path:

- encrypted RouterOS `.backup` generation;
- unique per-job backup password with encrypted-at-rest handling by NSM;
- optional `.rsc` export;
- outbound agent upload without FTP/SFTP on the router;
- chunked/Base64 transfer, offset validation, size limits, storage finalization and hash verification;
- temporary RouterOS file cleanup;
- safe `.rsc` viewer;
- same-Device text export comparison/diff with audit events.

The OptiWize FTP example is intentionally not used as the NSM backup architecture.

## MikroTik onboarding and agent

Implemented:

- one-time enrollment token bound to the intended Device;
- outbound RouterOS bootstrap workflow;
- RouterOS 7 preflight/device-mode checks where exposed;
- per-device credentials;
- agent heartbeat/polling;
- allow-listed remote jobs rather than arbitrary shell execution;
- modern and legacy RouterOS transport paths;
- modern source-generation syntax hardening;
- dynamic privilege profile for higher-risk allow-listed operations;
- reinstall/re-enrollment foundations without deleting the Device record.

### Installation verification and Agent Fleet

Implemented:

- per-device install state machine;
- token pending/expired, pairing complete, active credential, first heartbeat, verified/stale and suspected install/parser failure states;
- grace period after pairing;
- dedicated Agent workspace diagnostics;
- Agent Fleet KPIs and server-side filters;
- Action Center issue when pairing succeeds but post-install heartbeat does not arrive in the grace period;
- automatic recovery/issue resolution when the first valid heartbeat arrives;
- no raw agent secret/hash in the operational UI.

## MikroTik inventory, telemetry and workspace

Implemented:

- dedicated MikroTik Device workspace;
- identity, board/model, serial, primary MAC, architecture, software ID where exposed, RouterOS version, RouterBOOT version, uptime, CPU and memory data;
- historical modern-agent CPU/free+total-memory/uptime samples;
- derived memory-used percentage;
- Device metrics API and 1h/24h/7d/30d ranges;
- bounded downsampling;
- telemetry retention foundation;
- per-device Monitor workspace;
- real-device workspace UX refinements from later validation work.

Legacy transport remains capability-limited and is not claimed to provide the same telemetry contract.

## MikroTik configuration and health

Implemented on supported modern-agent paths:

- resource/system snapshot;
- IP addresses and routes;
- interfaces;
- firewall filter/NAT;
- active PPP sessions;
- DHCP leases;
- warning/error/critical logs;
- support snapshot;
- job-based collection/result upload.

Also implemented:

- stored `.rsc` configuration history;
- operator-approved per-device baseline;
- automatic comparison against baseline or previous export;
- suppression of volatile RouterOS export header noise;
- configuration drift Action Center issue creation/update;
- automatic drift issue recovery when configuration matches the approved baseline again;
- audit events for baseline approval, drift and comparison outcomes;
- dedicated MikroTik Interface Health worklist derived from interface snapshots;
- interface state filtering/search plus MAC/MTU/counter presentation where exposed;
- truthful legacy behavior: historical snapshot data can be viewed while refresh is not offered when capability is unavailable.

## MikroTik diagnostics

Implemented allow-listed jobs include:

- ping;
- traceroute;
- neighbor discovery;
- DHCP lookup;
- warning/error log retrieval;
- support snapshot where supported.

Results are executed through authenticated predefined jobs.

## MikroTik firmware and RouterBOOT

Implemented foundations/workflows include:

- firmware readiness;
- update channel/current/latest status collection from RouterOS update facilities;
- free-storage check;
- RouterBOOT current/upgrade firmware collection;
- firmware upgrade planning;
- package staging/download;
- explicit activation/reboot acknowledgement;
- post-reboot verification foundation;
- RouterBOOT staging and activation/reboot workflow;
- separate RouterOS and RouterBOOT lifecycle handling;
- privilege guard for firmware activation;
- firmware operational worklist.

This does not imply that an authoritative cross-vendor firmware/security advisory catalog already exists.

## Ubiquiti / UISP

Implemented as a read-only UISP Network connector:

- administrative connector configuration;
- encrypted API token storage;
- enable/disable and TLS verification settings;
- connection test;
- Device retrieval through UISP Network API;
- response limits/timeouts/error handling;
- Ubiquiti Device association by normalized MAC;
- preview before association;
- stable external UISP Device ID;
- duplicate/ambiguous association protection;
- manual Device refresh;
- current identity/model/serial/MAC/management IP/firmware/status/last-seen normalization;
- UISP Site/role/category retained as connector metadata rather than replacing NSM customer-local Sites;
- connector configuration/test/association/refresh audit events.

The connector is currently an inventory/association source; backup, firmware execution and full telemetry are not claimed unless separately implemented later.

## TP-Link / TR-069 foundations

Implemented foundations only:

- TP-Link/CPE vendor onboarding type;
- TR-069/ACS management-source model;
- onboarding validation requiring MAC or serial where applicable;
- capability-aware backup registry state that reports ACS/TR-069 backup as non-executable while the ACS integration is unavailable;
- UI wording that distinguishes the planned ACS path from executable capability.

No ACS northbound connector is claimed as implemented.

## Security and lifecycle foundations

Implemented:

- SecurityAdvisory persistence model;
- Device-to-advisory vulnerability impact model;
- Vulnerability worklist and detail/drill-down;
- search/filtering by CVE/vendor/product/severity/status/customer;
- affected Device/Customer counts;
- server-side pagination;
- lifecycle UI/data foundations;
- security/lifecycle data surfaced in customer/device workspaces where records exist.

Automated CVE ingestion/matching and authoritative EOL/EOS ingestion are not claimed as implemented.

## Deployment and CI foundations

Implemented in the repository/workflow:

- Alembic migration workflow;
- Docker Compose deployment foundations;
- app health/smoke validation;
- integrated smoke coverage for major workflows;
- dedicated MikroTik tests for enrollment, jobs, snapshots, diagnostics, firmware, RouterBOOT, backup, telemetry, install/fleet state, configuration drift, interface health and generated-source safety;
- production configuration/secrets kept outside committed runtime data.
